# PLAN.md — Job Application Tracker (MVP)

This file is the project's memory across Claude Code sessions. Claude Code has no memory between sessions, so **this file + git history are the source of truth for progress.** Read it at the start of every session; update it as you go.

Full spec: see `job-tracker-mvp-brief.md` in the repo root.

---

## Working protocol (read every session)

1. **Read `job-tracker-mvp-brief.md` and this file first**, then inspect the current state of the code before doing anything.
2. **Do exactly one milestone per session.** Complete only the milestone named in the prompt. Do **not** start the next milestone — stop when the current one is done and the app runs.
3. **Plan before executing.** Produce an execution plan for the milestone and wait for the user's approval before writing code.
4. **Commit after every working sub-step** with a clear message. Small, frequent commits mean an interrupted session loses only the uncommitted tail.
5. **Update this file as you go** — check off completed items and keep the "Current status" section accurate. The next session depends on it.
6. **End each milestone in a runnable, committed state.** The app should launch and the milestone's slice should work before you stop.
7. If you hit a blocker or make a decision worth remembering, note it under "Decisions & notes" below.

### M8 — AI job extraction from a screenshot  *(user request)* — ✅ done, live, and verified end-to-end

**Flow:** on the add-application form, a signed-in user clicks "Extract from screenshot," picks an image, and Claude Haiku 4.5 pre-fills company/role/salary/location/link/employment-type/work-mode for the user to review and save. Free but spend-capped (20 extractions/user/month, 5,000/month global ceiling, calendar-month reset) so usage can't produce a surprise bill.

- [x] `supabase/functions/extract-job-details/index.ts` — signed-in-only Edge Function; checks the per-user and global monthly quota BEFORE calling Anthropic (the wallet protection); calls Haiku 4.5 with the image + `output_config.format` structured-output JSON schema; records one `extraction_events` row per successful call. Curl-verified standalone (real extraction, invalid input, simulated over-quota) before any UI touched it, same discipline as M7.
- [x] `supabase/migrations/0004_extractions.sql` — `extraction_events(user_id, created_at)`, RLS scoped to `select` own rows only.
- [x] Token-spend caps added after real usage data (~1,093 in / 82 out ≈ $0.0015/extraction, cheaper than the original estimate): reject images over 5MB decoded before any Anthropic call; `max_tokens` 1024 → 500.
- [x] `extractJobDetails()` in `src/lib/remoteStore.ts`, reusing a shared `invokeEdgeFunction` helper (refactored out of the existing `callAccountAction` for the same error.context-extraction pattern).
- [x] "Extract from screenshot" button in `ApplicationForm.tsx` (add-mode + signed-in only — hidden entirely for guests and when editing), with client-side type/size validation mirroring the server's 5MB cap, a loading state, and auto-fill on success.
- [x] User-run live QA on the core extraction flow: passed (button appears when signed in, extracts correctly, re-usable, rejects non-images client-side).

#### Bug found and fixed during the QA round: structured-output schema rejected by Anthropic

First redeploy of the employment_type/work_mode extraction returned a generic "Extraction failed" (the function's deliberately-generic client-facing message for any non-2xx from Anthropic). Root cause: the schema expressed a nullable enum as `{ type: ['string', 'null'], enum: ['full_time', ..., null] }` — valid JSON Schema, but not a construct Anthropic's structured-output validator accepted, unlike the plain `type: ['string', 'null']` (no `enum`) used successfully by the original six fields. Fixed by switching to the documented-safe `anyOf` pattern: `{ anyOf: [{ type: 'string', enum: [...] }, { type: 'null' }] }`. Confirmed working after redeploy — worth remembering as a general pattern if a future field ever needs a nullable enum in a structured-output schema.

## Decisions & notes

The full decisions-and-gotchas log — stack choices, Supabase project/key facts, data-layer architecture, the guest-migration-trigger redesign, testing tooling, Edge Function deploy-sync rules, and every per-milestone bug post-mortem — lives in **[PLAN-ARCHIVE.md](PLAN-ARCHIVE.md)**. Record new decisions from the *current* active milestone here first; fold them into the archive at the next `/handoff` once that milestone is done.

**2026-08-01/02, AI extraction junk-handling session:**
- **Charging for blank/junk extractions is the final, standing design** — reversed from an initial refund-on-junk approach after live-measuring that a junk call costs ~99% as many tokens as a real one (the model has to read the whole input regardless of verdict). Refunding was giving away full-cost API calls for free. See "Current status" above for the full account.
- **Testing-cost discipline, learned the expensive way**: a synthetic-test-image diagnostic (spinning up headless Chrome via `puppeteer-core` to generate a fake "face" image, base64-encoding ~17KB inline into a browser `javascript_tool` call) burned ~30 minutes and the user's entire monthly extraction quota without root-causing anything (hit an unrelated 502). **Going forward: prefer real user-provided test assets over synthetic generation, and for any live API call needing image data, read the base64 from a file via Bash+curl+python3 rather than pasting large blobs into browser tool calls** — only small tokens (like a JWT) belong inline. This is now standing practice, not a one-off.
- The user's own already-authenticated browser session's `localStorage` JWT (`sb-fjlmyaamarnjlthbhycx-auth-token`) can be extracted and reused in `Authorization: Bearer` headers for direct `curl`/`fetch` testing against Supabase REST/Edge Function endpoints without going through the UI — useful for verifying RLS-scoped queries (e.g. `extraction_events`) or POSTing test payloads directly. Never persist the token to disk or commit it.

**2026-07-28, security review + domain migration session:**
- **exceljs → write-excel-file**, not a pin-and-CI-gate-only fix. `npm audit fix` had no non-breaking path (only `--force` → exceljs 3.4.0, breaking); `write-excel-file`'s only dependency is `fflate`, 0 advisories, browser+Node support. exceljs kept as a **devDependency only**, purely to read files back in `xlsxExport.test.ts` — never ships to the browser bundle, so its advisories don't apply there and `npm audit --omit=dev` (now in CI) stays clean.
- **Newsletter double opt-in is deliberately decoupled from beta access.** `newsletter-subscribe` no longer adds to the Resend audience directly — it inserts a pending row and emails a confirmation link; only clicking that link (new `newsletter-confirm` function) touches Resend. But `LandingPage.tsx`'s `onSubscribed`/beta-access grant only ever depended on the initial POST succeeding, so this closes list-bombing/consent-evidence without adding any friction to the beta funnel shipped the same day. **Reverted 2026-07-29** — see that session's entry below; double opt-in lasted about 24 hours before the user found the resulting email UX confusing enough to accept the anti-abuse tradeoff back.
- **Cloudflare API token is zone-scoped**, not account-wide — confirmed by trying it against the newly-created `offertrail.app` zone and getting `Unauthorized` on every call (even `/user/tokens/verify`). Don't assume a working Cloudflare token call against one zone means it'll work against another; check per-zone.
- **Domain migration: full decommission of jobtracker.fazare.dev, not a redirect** — explicit user choice against my recommendation. Accepted consequence: the published Chrome extension (hardcoded to the old domain in its manifest) breaks the moment the old domain is decommissioned, until a new version is submitted and approved by the Chrome Web Store — review time is outside any session's control.
- `jobtracker.fazare.dev` is a **Worker Custom Domain binding** (Cloudflare `workers/domains` API: `{hostname, service: "job-tracker", environment: "production"}`), not a DNS CNAME + Pages setup — worth knowing before assuming DNS records are the lever to pull for any future domain work.

**2026-07-29, email branding + newsletter opt-in session:**
- **`git status`/`git ls-files` is the fast, reliable check for "is this asset actually deployed" — faster than debugging Cloudflare/Worker config first.** The `public/brand/*` bug (see "Current status") looked at first like it could be an asset-routing or SPA-fallback problem; it took one `git ls-files public/` to see the files were never tracked at all. Worth trying this check early any time a *known-to-exist* static file 404s or fallback-serves in production but works locally.
- **A `200` response with `content-type: text/html` from a path that should be an image is the tell for "SPA fallback served instead of the real asset"** — not a `404`. This project's Cloudflare Worker uses `not_found_handling: "single-page-application"` (`wrangler.jsonc`), so any missing static path silently returns `index.html` with `200`, not an error. Compare against a known-good asset (e.g. `favicon.svg`) to confirm it's path-specific, not a general asset-serving failure, before assuming the Worker config itself is broken.
- **`@supabase/auth-js`'s actual installed default is `flowType: 'implicit'`** (confirmed by reading `node_modules/@supabase/auth-js/dist/main/GoTrueClient.js:24` directly, version 2.110.6) — don't assume PKCE is the default without checking the installed version's source; this project's `createClient()` call never sets `flowType` explicitly, so whatever the installed package defaults to is what's live. This ruled out a plausible-sounding PKCE/cross-device theory for the confirmation-link bug and pointed at the real cause (stale `redirect_to`/Site URL) instead — a reminder that a plausible mechanism isn't confirmation; check the actual link/config before committing to a diagnosis.
- **Newsletter single-opt-in vs. double-opt-in is an explicit, revisited tradeoff, not a settled decision** — the user chose single opt-in this session fully aware it reopens the Finding #6 list-bombing gap (rate-limiting is the only remaining guard). If this becomes a real abuse problem later, the double-opt-in code isn't gone, just reverted in git history (`ec0cf35` → hardening added, `90fd35e` → single-opt-in reversion) — re-applying it would look similar to the original Finding #6 fix rather than needing a from-scratch redesign.
- **Edge Function redeploys in this repo are dashboard-paste, one file at a time, and each carries its own duplicated helper code** (e.g. `buildEmailHtml()` exists separately, near-identically, in both `account-action/index.ts` and `newsletter-subscribe/index.ts`) — this is deliberate given the no-CLI-link deploy model, not an oversight to "clean up" by extracting a shared import later, unless the deploy model itself changes first.
